# Supabase Migration Design

**Date:** 2026-03-18
**Project:** Signal Scheduler
**Goal:** Replace ephemeral JSON file storage with Supabase for persistent schedules and logs across restarts/redeploys.

---

## Problem

Schedules and logs are stored in `schedules.json` and `logs.json` on the local filesystem. On Replit/Cloud Run, these files are wiped on every restart or redeploy, losing all user data.

---

## Solution

Migrate data persistence to Supabase (PostgreSQL) using the `@supabase/supabase-js` SDK. Introduce a `groups` feature to organize schedules and enable filtering.

---

## Database Schema

### `groups`
| Column | Type | Notes |
|--------|------|-------|
| `id` | `text` PK | uuid (seeded: `'general'`) |
| `name` | `text` UNIQUE NOT NULL | e.g. "General", "Marketing" |

Seeded with one default row: `{ id: 'general', name: 'General' }`.

### `schedules`
| Column | Type | Notes |
|--------|------|-------|
| `id` | `text` PK | uuid generated by app |
| `name` | `text` NOT NULL | |
| `group_id` | `text` FK → groups NOT NULL | defaults to `'general'` |
| `type` | `text` NOT NULL | once/minutes/hours/daily/weekly |
| `params` | `jsonb` NOT NULL | all schedule-type-specific fields |
| `webhook_url` | `text` NOT NULL | |
| `is_active` | `boolean` NOT NULL | default `true` |
| `created_at` | `timestamptz` NOT NULL | default `now()` |

### `logs`
| Column | Type | Notes |
|--------|------|-------|
| `id` | `text` PK | uuid generated by app |
| `schedule_id` | `text` | nullable (survives schedule deletion) |
| `schedule_name` | `text` | denormalized for readability |
| `time` | `timestamptz` | when the webhook fired |
| `webhook_url` | `text` | |
| `status` | `text` | `'Success'` or `'Failed'` |
| `response` | `text` | HTTP status or error message |

`schedule_name` is intentionally denormalized so log entries remain readable even after the source schedule is deleted. Logs are never deleted automatically — `getLogs()` queries the latest 50 by `time DESC`.

## SQL Setup

Run once in Supabase Dashboard → SQL Editor:

```sql
CREATE TABLE groups (
  id text PRIMARY KEY,
  name text UNIQUE NOT NULL
);

INSERT INTO groups (id, name) VALUES ('general', 'General');

CREATE TABLE schedules (
  id text PRIMARY KEY,
  name text NOT NULL,
  group_id text NOT NULL REFERENCES groups(id) DEFAULT 'general',
  type text NOT NULL,
  params jsonb NOT NULL DEFAULT '{}',
  webhook_url text NOT NULL,
  is_active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE logs (
  id text PRIMARY KEY,
  schedule_id text,
  schedule_name text,
  time timestamptz,
  webhook_url text,
  status text,
  response text
);
```

## Architecture

### New file: `db.js`

All Supabase queries are isolated in a single `db.js` module at the project root. `index.js` only imports and calls these functions — no Supabase client or query logic in `index.js`.

```
db.js exports:
├── getSchedules()            → SELECT all schedules + group name (join)
├── getScheduleById(id)       → SELECT single schedule by id
├── createSchedule(data)      → INSERT into schedules, return inserted row
├── updateSchedule(id, data)  → UPDATE schedule by id, return updated row
├── deleteSchedule(id)        → DELETE schedule by id
│
├── getGroups()               → SELECT all groups
├── findOrCreateGroup(name)   → find OR insert group by name, return id
│
├── getLogs()                 → SELECT latest 50 logs ORDER BY time DESC
├── addLog(log)               → INSERT into logs
└── clearLogs()               → DELETE all logs
```

Supabase client initialized once at top of `db.js`:
```js
const { createClient } = require('@supabase/supabase-js');
const supabase = createClient(process.env.SUPABASE_URL, process.env.SUPABASE_KEY);
```

### Changes to `index.js`

- Remove `fs`, `path` imports
- Remove `dataFile`, `logsFile` constants
- Remove `getJson`, `saveJson`, `getSchedules`, `saveSchedules`, `getLogs`, `addLog` functions
- Add `const db = require('./db')`
- Replace all data calls with `db.*` equivalents
- Add `await` at ~15 call sites
- `initSchedules()` becomes `async` (loads from DB on startup)
- `triggerWebhook()` already async — update internal calls to use `db.*`

### Frontend changes (`public/script.js`)

- Add group field to schedule creation/edit form
- Group input: combo — shows dropdown of existing groups, allows typing new name
- Filter bar: buttons/tabs per group to filter the schedule list
- Schedules API response will include `group_name` from join

| `SUPABASE_KEY` | Supabase → Settings → API → anon/public key | Replit Secrets |

## Setup Steps

1. Create new Supabase project at supabase.com
2. Run SQL above in Supabase SQL Editor
3. Copy Project URL and anon key → add to Replit Secrets
4. Run `npm install @supabase/supabase-js`

## Key Decisions

| Decision | Choice | Reason |
|----------|--------|--------|
| SDK vs raw SQL | `@supabase/supabase-js` | Official, simpler, handles auth automatically |
| Data layer isolation | Separate `db.js` | Keeps `index.js` clean; Supabase dependency is contained |
| Log retention | Keep all logs forever | Storage is cheap; display latest 50 |
| Group default | "General" (seeded in DB) | Every schedule must belong to a group; no nulls |
| `schedule_name` in logs | Denormalized | Logs remain readable after schedule deletion |
